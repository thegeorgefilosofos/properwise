# Καστάνια

Μια καστάνια είναι αριθμός που **μόνο κατεβαίνει**. Δεν είναι στόχος· είναι
απόδειξη ότι κάτι που βελτιώθηκε δεν θα χειροτερέψει σιωπηλά.

## Ο κανόνας, ολόκληρος

1. **Ο αριθμός μόνο κατεβαίνει.** Αν ανέβει, ο έλεγχος κοκκινίζει.
2. **Η βάση χαμηλώνει στο ΙΔΙΟ commit** που έφερε τη βελτίωση. Οχι στο επόμενο.
3. **Με γραπτή σημείωση στα ελληνικά**, δίπλα στον αριθμό, που λέει τι άλλαξε.
4. **Πτώση χωρίς χαμήλωμα της βάσης είναι κι αυτή αποτυχία.** Αλλιώς η βάση
   ξεμένει ψηλά, κρύβει μελλοντική χειροτέρευση και η καστάνια γίνεται
   διακοσμητική.

Το τρίτο και το τέταρτο είναι που κάνουν τη διαφορά. Χωρίς αυτά έχεις ένα
νούμερο που κανείς δεν θυμάται γιατί είναι εκεί.

## Πού ζουν

| Αρχείο | Τι μετρά | Εντολή |
|---|---|---|
| `docs/perf/budget.json` | bytes καλωδίου (gzip) ανά δημόσια οθόνη | `npm run perf:budget` |
| `docs/perf/server.json` | bytes ίχνους ανά ανάπτυξη και ανά συνάρτηση | `npm run perf:server` |
| `docs/perf/bench.json` | χρόνος απόδοσης με 200 ακίνητα | `npm run perf:bench` |
| `docs/perf/mobile.json` | το ίδιο, σε προφίλ κινητού | `npm run perf:mobile` |

Το σχήμα είναι σταθερό και η πρώτη γραμμή είναι πάντα η σημείωση:

```json
{
  "note": "Bytes ΙΧΝΟΥΣ ανά ανάπτυξη, από τα .nft.json παραγωγικού build. Το όριο μόνο κατεβαίνει.",
  "slack": 0.08,
  "total": 173601043,
  "heaviest": 6689040,
  "heaviestRoute": "/accountant/workspace/page.js",
  "functions": 44
}
```

Το `slack` είναι η ανοχή θορύβου: 8%. Δεν είναι άδεια να χειροτερέψεις κατά 8%·
είναι παραδοχή ότι δύο build δεν βγάζουν ποτέ ακριβώς το ίδιο byte.

Υπάρχουν και καστάνιες που δεν είναι απόδοση: το χρέος lint (`npm run
lint:ratchet`), οι κλίμακες σχεδίασης (`design-scale-baseline.json`), το χρώμα
(`color:ratchet`). Ιδιος κανόνας.

## Τα βήματα

### 1. Μέτρησε ΠΡΙΝ, στο ίδιο μηχάνημα

```
npm run build
npx next start -p 3100 &
node scripts/perf-budget.mjs; echo "κωδικός: $?"
```

### 2. Κάνε την αλλαγή, μέτρα ΜΕΤΑ, ζευγαρωτά

**Οχι «όλα τα Α και μετά όλα τα Β».** Σε μηχάνημα που μοιράζεται πυρήνες, η
σειρά μετράει περισσότερο από την αλλαγή. Α, Β, Α, Β — και σύγκρινε ζεύγη.

Το περιστατικό που το γέννησε: μια μέτρηση έδειξε **509 ms** διαφορά. Με
ζευγαρωτή μέτρηση η πραγματική διαφορά ήταν **7 ms**. Τα υπόλοιπα 502 ήταν
θόρυβος και κόστισαν μια μέρα.

### 3. Γράψε τη νέα βάση

```
node scripts/perf-budget.mjs --write
```

Μετά **άνοιξε το αρχείο και γράψε τη σημείωση**. Ο διακόπτης γράφει αριθμούς,
όχι λόγους. Η σημείωση λέει τι άλλαξε, όχι πόσο:

> «Το `sharp` έφυγε από το ίχνος με `outputFileTracingExcludes`: δεν το καλεί
> καμία διαδρομή, γιατί το `next/image` δεν χρησιμοποιείται πουθενά.»

### 4. Ο έλεγχος πρέπει να είναι πράσινος και ΜΕΤΑ την εγγραφή

```
npm run perf:budget; echo "κωδικός: $?"
```

Αν είναι ακόμη κόκκινος, η βάση γράφτηκε λάθος ή η μέτρηση δεν ήταν σταθερή.

### 5. Ενα commit και τα δύο μέσα

Η αλλαγή και η νέα βάση δένονται μαζί. Το μήνυμα λέει τον παλιό αριθμό, τον
νέο και το γιατί. Αν η βάση μπει σε ξεχωριστό commit, η ιστορία δείχνει μια
βελτίωση χωρίς αιτία και μια αλλαγή χωρίς αποτέλεσμα.

## Τι ΔΕΝ κάνεις ποτέ

- **Δεν ανεβάζεις βάση** για να περάσει το CI. Αν το νούμερο ανέβηκε, κάτι
  χειροτέρεψε· αυτό είναι το εύρημα, όχι η βάση.
- **Δεν αυξάνεις το `slack`.** Η ανοχή υπάρχει για θόρυβο μέτρησης. Οποιος τη
  μεγαλώνει για να χωρέσει μια χειροτέρευση, σβήνει την καστάνια.
- **Δεν γράφεις βάση από μέτρηση σε άλλο μηχάνημα** ή με άλλο φορτίο.
- **Δεν αφήνεις πτώση αχαμήλωτη.** Ο έλεγχος κοκκινίζει και σε αυτό, επίτηδες.
- **Κανένα bot δεν αγγίζει αυτά τα αρχεία.** Το `docs/perf/*.json` είναι στις
  προστατευμένες διαδρομές του `docs/org/SYNERGEIA.md`: αλλάζουν μόνο από
  άνθρωπο, με μέτρηση που έγινε στο χέρι.

## Και ποτέ μέσα από σωλήνα

```
node scripts/perf-budget.mjs; echo "κωδικός: $?"      ← έτσι
node scripts/perf-budget.mjs | tail -5                ← ποτέ
```

Ο κωδικός εξόδου ενός σωλήνα είναι του `tail`, που πάντα επιτυγχάνει. Κόκκινη
μέτρηση περνά για πράσινη.
